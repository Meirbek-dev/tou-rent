# apps/e2e - сквозные сценарии Правил (гейт G11)

Playwright-прогон против поднятого стенда: демо-сценарий ТЗ § 9.1 (T14),
приемка контура 2 (T32) и приемка контура 3 (T44) - ТЗ § 10в.

## Запуск

```bash
vp run stack:up            # api :8080, PostgreSQL, Redis, RustFS
vp run dev                 # web :3000
bun run --cwd apps/e2e e2e:install   # один раз: браузер chromium
bun run --cwd apps/e2e e2e
```

Отдельный файл сценариев - `bun run --cwd apps/e2e e2e -- loop3-acceptance.spec.ts`.

Переменные прогона:

- `E2E_BASE_URL` - адрес web (вторая dev-сессия слушает :3105);
- `E2E_PASSWORD` - пароль seed-аккаунтов (по умолчанию - пароль локального стенда);
- `E2E_PROVISION_CMD` - команда подготовки площадки, `{}` заменяется подкомандой
  api; по умолчанию `podman exec tou-rent-dev-api-1 cargo run -q -p api -- {}`.

## Что покрыто

### Демо-сценарий § 9.1 (`demo-scenario.spec.ts`)

1. **Организатор** - объект имущества (FR-101) → расшифровка ставки Прил. 4
   (FR-201) → тендер с лотом (FR-301) → даты и публикация (FR-303: ≥10 дней
   до вскрытия) → карточка на публичном портале (FR-1401) и PDF объявления.
2. **Комиссия и торги** - вскрытие открывает запечатанные цены (FR-403,
   INV-040) → двое допущены, один отклонен с основанием п. 52 (FR-502,
   INV-052) → протокол допуска PDF (FR-503) → уведомление допущенных (FR-504)
   доходит до колокольчика участника (FR-1301) → комната торгов, две сессии
   в разных контекстах браузера торгуются в реальном времени (FR-601, FR-603,
   INV-063) → определение победителя (FR-606) → протокол итогов PDF (FR-701).

### Приемка контура 2, ТЗ § 10в (`loop2-acceptance.spec.ts`)

1. **Полный тендер до договора** - договор из итогов торгов (FR-901, п. 108)
   → шаги конвейера п. 110–115 по порядку (FR-902) → INV-115: подпись
   наймодателя недоступна, пока перечень сверки п. 113 не отмечен целиком →
   регистрация в журнале (FR-905, п. 126) → акт приема-передачи (FR-904,
   п. 122) → досье собралось само и выгружается архивом (FR-1602).
2. **Несостоявшийся → повтор** - основание п. 81.2 выведено из фактов
   (FR-801) → признание и протокол о несостоявшемся (FR-802) → организатор
   объявляет повторный тендер: черновик со ссылкой `repeat_of` и лотами (п. 82).
3. **Победитель уклонился → № 2** - уклонение с основанием п. 116 (FR-903) →
   договор прекращен, взнос удержан (счет взноса обнулен, п. 116) → протокол
   о победителе № 2 и уведомление (п. 117–118) → договор с участником № 2
   на его ставку из торгов.

### Приемка контура 3, ТЗ § 10в (`loop3-acceptance.spec.ts`)

1. **Особый порядок: инвестор** - заявка инвестиционной категории с объемом
   инвестиций (FR-1201, Прил. 3) → заключение уполномоченного подразделения
   (FR-1202, п. 89) → решение Правления «предоставить» (п. 90) → досье решения
   собралось само и выгружается архивом (FR-1206, п. 97) → результат
   опубликован и виден гостю на портале (FR-1403) → инвестиционный договор:
   ставка - снимок расчета Прил. 4, комплект приложений п. 91 еще не собран,
   и договор не подписывается (FR-1204, INV-091).
2. **Особый порядок: почасовая** - почасовая ставка считается от 2 МРП/час
   (FR-205, п. 97) → заявка → заключение → решение → публикация результата
   и запись факта в досье (FR-1403, FR-1206) → решение попало в реестр
   отчетности (арх. § 9).

## Почему сценарии идут на подготовленных тендерах

Публикация требует ≥10 календарных дней до вскрытия (FR-303), поэтому
довести свежесозданный тендер до вскрытия - и тем более до торгов - внутри
одного прогона невозможно. Площадки готовят подкоманды api (та же логика,
что у seed Прил. Б, заголовок уникален для каждого прогона):

| Подкоманда                    | Что дает                                                                                                   |
| ----------------------------- | ---------------------------------------------------------------------------------------------------------- |
| `api demo-tender`             | «горячий» тендер § 9.1: три заявки, прием закрыт, заседание настало                                        |
| `api demo-summed-up`          | тендер с завершенными торгами: двое допущены и внесли взносы, победитель и второе место из реальных ставок |
| `api demo-single-application` | тендер с единственной заявкой и истекшим приемом (основание п. 81.2)                                       |
| `api demo-special-site`       | площадка контура 3: свой объект на прогон и помеченная инвестиционная категория (Q-013)                    |

Площадка `demo-summed-up` получает **свой объект имущества и своих
участников**: договор доходит до регистрации (один объект не сдается на
пересекающиеся периоды - INV-DB-02), а сценарий уклонения навсегда заносит
победителя в реестр уклонистов (FR-505) - демо-аккаунты после него не
проходили бы допуск в других прогонах.

По той же причине свой объект получает и площадка контура 3: сценарий
инвестора доходит до договора. Инвестиционную категорию площадка помечает
сама - какая из тринадцати категорий п. 87 инвестиционная, Правила агенту
не сообщают (Q-013), а без пометки правило приоритета большей суммы
(FR-1203) не включается ни для одной и договор не заключить.

## Трассировка требований

Контур принимается, когда каждое FR закрыто тестом с привязкой к ID
(ТЗ § 10в). Это проверяет гейт `fr_traceability` в `crates/testkit`: он
читает ТЗ, берет требования контура 3 и требует, чтобы ID упоминался
в файле с проверками - доменном тесте, testkit или здесь, в e2e.
Единственное объявленное исключение - FR-1303 (задача T41 пропущена
по решению заказчика).

## CI

Гейт G11 включен в `.gitlab-ci.yml` job'ом `e2e` (T31): Playwright гоняется
против api и web, поднятых в самом job'е, с сервисами PostgreSQL/Redis/RustFS.
Пайплайн ждет аппрува инженера - `.gitlab-ci.yml` защищен регламентом А.4
(A-030, A-063).
