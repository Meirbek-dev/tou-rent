# ADR-0003: Zitadel как провайдер идентичности вместо Keycloak

Статус: accepted · 2026-08-07 · связано: FR-1502, T18

## Контекст

Арх. § 2 и ТЗ FR-1502 закладывают на контур 2 Keycloak с LDAP-федерацией с AD
университета. Указание заказчика (07.08.2026): использовать Zitadel.

Требования к провайдеру не меняются: сотрудники входят учетными записями AD,
внешние участники регистрируются сами, сессии остаются серверными (Redis),
доменная модель `User` не переписывается - меняется только источник субъекта.

## Решение

- Провайдер идентичности - Zitadel (self-hosted контейнер рядом с остальным
  стендом, своя база в том же PostgreSQL-инстансе).
- Протокол - OIDC authorization code + PKCE; api выступает конфиденциальным
  клиентом, обмен кода на токены и разбор `id_token` - на стороне api
  (крейт `openidconnect`), браузер токенов не видит.
- После успешного входа api заводит/находит запись `core.users` по паре
  `(issuer, subject)` и кладет в сессию тот же `user_id`, что и локальный вход
  (FR-1501). Все, что построено на `CurrentUser`, продолжает работать.
- Федерация с AD - настройка на стороне Zitadel (LDAP IdP), кода в
  репозитории не требует; в приложении фиксируется только доверенный issuer.
- Локальный вход email+пароль сохраняется: участники и демо-стенд, а также
  аварийный доступ админа при недоступном провайдере.

## Альтернативы

- Keycloak (арх. v2). Отклонено указанием заказчика.
- Только локальная auth (контур 1). Не закрывает FR-1502: сотрудники должны
  входить учетными записями AD, отдельные пароли в системе - лишний контур
  утечки.
- Публичный клиент с токенами в браузере. Отклонено: ломает серверную
  сессионную модель и CSRF double-submit, токены попадают в JS-контекст.

## Следствия

- Появляется внешняя зависимость на пути входа сотрудников; локальный вход -
  якорь отката, переключается конфигурацией (без `OIDC_*` переменных api
  работает как в контуре 1).
- Роли сотрудников приходят из Zitadel claim'ом и отражаются в
  `core.role_grants` - источник истины по правам остается в БД (INV-POL-01,
  аудит FR-1503).
- Смена провайдера в будущем стоит настроек, а не кода: в api фиксируются
  только issuer, client_id/secret и правило маппинга ролей.
