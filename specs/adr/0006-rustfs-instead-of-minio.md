# ADR-0006. RustFS вместо MinIO как объектное хранилище

- Статус: accepted (2026-08-10)
- Контекст: арх. § 2, § 5; INV-042, ADR-0004, NFR-09, NFR-10

## Контекст

Архитектура называет хранилищем файлов MinIO. Приложение работает с ним
не напрямую, а через `object_store` по S3 API: в коде нет ни одной строки,
знающей вендора, - только адрес, ключи и имя бакета (`crates/http/src/storage.rs`).
Значит, замена сервера - вопрос инфраструктуры, а не переписывания слоя.

От хранилища эта система требует трех вещей: S3 API для `object_store`,
Object Lock в режиме compliance на бакет досье (INV-042, ADR-0004) и
учетные записи с политиками, чтобы приложение не ходило root-ключами
(NFR-09).

## Решение

**Хранилище - RustFS** (`rustfs/rustfs:1.0.0-rc.1`), одна нода, один диск.

1. **Приложение не меняется.** Меняются `S3_ENDPOINT` и образ в compose.
   Адресация остается path-style: virtual-hosted в RustFS требует
   отдельно настроенных доменов (`RUSTFS_SERVER_DOMAINS`), а стенду
   это не нужно.
2. **Бакеты заводит `aws-cli`, а не клиент вендора.** Создание бакета
   с Object Lock и `PutObjectLockConfiguration` - обычные вызовы S3;
   привязывать этот шаг к клиенту конкретного сервера незачем, и следующая
   замена сервера его снова не заденет.
3. **IAM заводит `rc`** (`rustfs/rc`, клиент RustFS). Управление
   пользователями и политиками живет в admin-API, а он у каждого сервера
   свой: `mc admin` от MinIO с RustFS не работает (A-093).
4. **Политика приложения потеряла `s3:DeleteObject` на `dossiers`.**
   Единственным ее потребителем была компенсация осиротевшего объекта
   при отказе БД - см. ниже.

## Альтернативы

- **Остаться на MinIO.** Ничего не стоит и ничего не дает; решение
  о переходе принято заказчиком.
- **Взять `rc` и на бакеты.** Один клиент вместо двух, но у `rc` нет
  команд Object Lock, а INV-042 - не то место, где стоит полагаться
  на недокументированное поведение.
- **Заводить бакет из приложения при старте.** Убрало бы шаг
  провижининга, но потребовало бы выдать приложению `s3:CreateBucket` -
  ровно то право, которым снимают Object Lock, создав бакет заново.

## Следствия

- Прод-стенд получил два разовых шага вместо одного: `rustfs-init`
  (бакеты, WORM) и `rustfs-iam` (учетная запись приложения).
- Object Lock в RustFS моложе, чем в MinIO: сообщения о том, что
  compliance-режим не удерживал объект, в трекере есть, но закрыты
  (`alpha.79`, `beta.6`). На `1.0.0-rc.1` режим проверен на дев-стенде:
  объект наследует срок бакета, удаление версии root-ключами -
  AccessDenied (A-094). Прод-конфигурация (compliance/5 лет плюс политика
  `tou-rent-app`) дополнительно проверена 10.08.2026 на прод-compose,
  поднятом локально (T75). На реальном проде проверку все равно надо
  повторить: второй рубеж INV-042 (`retain_until` в БД, append-only
  таблица досье) от этого никуда не девается.
- Оба разовых шага идемпотентны на практике, а не только по замыслу:
  при повторном `up -d` они отработали заново без ошибок (`create-bucket`
  и `policy create` прикрыты `|| true`).
- Том переименован `minio_data` → `rustfs_data`, то есть новый стенд
  поднимается пустым. Если на стенде уже лежат объекты, перенос - явный
  отдельный шаг (`mc mirror` из старого тома в новый бакет **до** включения
  Object Lock), а не побочный эффект деплоя: WORM не позволит переписать
  то, что залилось не так.
