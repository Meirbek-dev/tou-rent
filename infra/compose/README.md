# infra/compose

- `docker-compose.dev.yml` - локальный стенд: PostgreSQL 19beta (ADR-0002), Redis 8, RustFS (ADR-0006).

  ```bash
  podman compose -f infra/compose/docker-compose.dev.yml up -d
  ```

  Профиль `api` (`vp run stack:up`) добавляет api в контейнере: миграции идут
  до старта, health - `GET /api/v1/healthz`. Вместе с api поднимается воркер
  `jobs` (сроки FR-1702, снятие протоколов и публикаций особого порядка
  через 6 месяцев - INV-076, FR-1403; интервал `JOBS_INTERVAL`).

  Ключ шифрования цен (INV-040, п. 40) задан в compose дев-значением
  `PRICE_ENCRYPTION_KEY`: без него api не читает и не пишет ценовые
  предложения. Тот же ключ нужен контейнерным прогонам тестов testkit.

  Бакет `dossiers` создается с Object Lock (INV-042, FR-1206, FR-1602,
  п. 16.15, 42): материалы досье не удаляются до истечения срока хранения.
  Блокировка включается только при создании бакета - на стенде, где `dossiers`
  уже создан без нее, WORM появится после пересоздания тома
  (`podman volume rm tou-rent-dev_rustfs_data`). Срок каждого материала ведет БД
  (`core.dossier_items.retain_until`): пять лет тендерным, три года решениям
  особого порядка.

  Redis на стенде идет без пароля и без сохранения на диск - в отличие от
  прода, где он закрыт `REDIS_PASSWORD` и пишет AOF (см. ниже). Сессии стенда
  переживать перезапуск не обязаны, а вот прод-сессии - обязаны.

  Режим блокировки на стенде и в проде разный (A-098): здесь governance на
  сутки, в проде compliance на пять лет. Стенд проверяет, что блокировка
  включена и удаление отбивается, а не длину срока; compliance же не снимает
  никто, включая администратора, - каждый пробный файл досье оставался бы на
  диске разработчика пять лет.

## Провайдер идентичности Zitadel (FR-1502, ADR-0003)

Профиль `zitadel` поднимает Zitadel рядом со стендом и настраивает его
скриптом `infra/zitadel/provision.sh` (проект, роли ТЗ § 3, OIDC-клиент api,
демо-сотрудник). Стенду он не обязателен: без него api работает на локальном
входе контура 1 (FR-1501).

Адрес провайдера - `id.127.0.0.1.nip.io:8081`, один и для браузера, и для api:
`iss` в `id_token` обязан совпадать с адресом discovery, иначе проверка токена
не пройдет. Правки hosts не нужны: `*.127.0.0.1.nip.io` резолвится публичным
DNS в 127.0.0.1 (браузер попадает на опубликованный порт), а внутри сети
стенда тот же адрес перехватывает сетевой алиас на контейнер Zitadel.

Если корпоративный DNS не отдает `nip.io`, замените домен в
`docker-compose.dev.yml` (`ZITADEL_EXTERNALDOMAIN`, сетевой алиас и URL в
`zitadel-init`) на любой другой и добавьте его в hosts машины.

```bash
vp run zitadel:up          # Zitadel API (:8081) + Login V2 (:3002) + провижининг
vp run api:restart         # api подхватывает infra/compose/.zitadel/oidc.env
```

- Консоль Zitadel - <http://id.127.0.0.1.nip.io:8081>, вход `admin@tou.id.127.0.0.1.nip.io`
  (пароль - `ZITADEL_ADMIN_PASSWORD`, по умолчанию dev-значение из compose).
- Login V2 - <http://id.127.0.0.1.nip.io:3002/ui/v2/login>; начиная с Zitadel v4
  интерфейс входа работает отдельным контейнером `zitadel-login`.
- Демо-сотрудник провайдера - `secretary@tou.local` (`ZITADEL_DEMO_PASSWORD`);
  роли `secretary` и `commission` приезжают в систему claim'ом.
- `infra/compose/.zitadel/oidc.env` - реквизиты клиента, генерируются, в git
  не попадают (NFR-09). Пересоздать: удалить файл и `vp run zitadel:provision`.
- Федерация с AD университета настраивается в самом Zitadel (LDAP IdP) -
  кода в репозитории не требует.

## Прод (NFR-10)

- `docker-compose.prod.yml` - Caddy → web/api, PostgreSQL, Redis, RustFS,
  воркер `jobs` (тот же образ, что api, другая команда) и разовый `api-migrate`,
  который накатывает миграции до старта api. Версии инфраструктурных образов
  пиньованы (T70): с `latest` два деплоя одной ревизии кода дают разные стенды,
  а откатиться некуда - тег уже переехал. Обновление версии - отдельный коммит.
  Образы api и web собираются из `infra/docker/*.Dockerfile` и публикуются в
  GitLab Container Registry (job публикации добавляется отдельным MR -
  `.gitlab-ci.yml` защищен регламентом А.4).
- Хранилище настраивается двумя разовыми шагами: `rustfs-init` заводит бакеты
  (`dossiers` - с Object Lock и compliance-сроком на пять лет), `rustfs-iam` -
  учетную запись приложения с политикой `tou-rent-app`. Политика на `dossiers`
  дает только `s3:GetObject`, `s3:PutObject` и `s3:ListBucket`: удаление там
  запрещено самим WORM, и лишнее право у приложения не хранится (INV-042).
  Удаление остается на `public` - снятие публикаций через 6 месяцев штатно
  (INV-076, FR-1403). Root-ключами (`S3_ACCESS_KEY`) ходят только эти два шага.
- `Caddyfile` - TLS Let's Encrypt на `$TOU_DOMAIN`, `/api/*` на api (с
  отключенной буферизацией: SSE-уведомления и WS-комната торгов), остальное на web.
- Redis закрыт паролем (`REDIS_PASSWORD`) и пишет AOF: в нем сессии и счетчики
  попыток входа, и до T74 всякий перезапуск разлогинивал всех разом. Работает он
  под `user: "999:999"` (A-101): штатный вход образа снимает права до `redis` сам,
  но только при наличии SETUID и SETGID, а их снимает `cap_drop` - без явного
  пользователя сервер оставался root'ом и падал на первом же старте с AOF
  («Can't open or create append-only dir»). При смене версии образа сверьте uid.
- У контейнеров есть потолки памяти (A-099) и снятые привилегии
  (`no-new-privileges`, `cap_drop: [ALL]`; Caddy оставлен `NET_BIND_SERVICE`,
  Postgres - минимум для штатного входа образа). Потолки рассчитаны на хост
  с 16 ГБ - под другой объем правятся в блоке `x-hardening`/`mem_limit`.
- У `jobs` проба здоровья выключена намеренно (A-102): воркер берет образ api
  вместе с его `HEALTHCHECK` на `/api/v1/healthz`, а портов не слушает - с ней
  контейнер вечно unhealthy при штатной работе. Живость воркера видна по журналу.
- `.env.prod.example` - перечень переменных; рабочая копия `.env` рядом, в git не попадает.
  Среди них `PRICE_ENCRYPTION_KEY` - мастер-ключ шифрования ценовых предложений
  (INV-040): в базе он не хранится, поэтому его копия нужна отдельно от дампов,
  иначе цены прошлых тендеров станут нечитаемыми.
- `resync-migration-checksums.sh` - пересчет контрольных сумм примененных
  миграций. Нужен ровно в одном случае: в файле миграции поправили комментарий,
  и sqlx отказывается стартовать с `migration NNN ... has been modified`.
  Схему скрипт не трогает и для правок SQL не предназначен - изменение схемы
  всегда новой миграцией (A-063, A-096).

  ```bash
  PSQL="podman exec -i tou-rent-dev-postgres-1 psql -U tou_rent -d tou_rent" \
    ./resync-migration-checksums.sh --apply
  ```

- `deploy.sh` - пулл образов → миграции → `up -d` → ожидание `/healthz` у api
  и у web → откат при неудаче.

  ```bash
  cd infra/compose && cp .env.prod.example .env   # заполнить секреты
  ./deploy.sh
  ```

  **Окно заморозки:** скрипт отказывается деплоить, пока жива хоть одна комната
  торгов (`core.auctions.status = 'running'` и срок не истек) - обрыв WS-комнаты
  посреди процедуры недопустим (п. 63–68). Заморозку задает именно комната, а не
  статус тендера: тендер может висеть в `trading` с уже завершенными торгами,
  в том числе в демо-данных Прил. Б. Осознанный обход - `DEPLOY_FORCE=1`.

  **Откат:** тег, прошедший проверку здоровья, записывается в `.deployed-tag`
  рядом со скриптом (файл принадлежит хосту и в git не попадает). Если новая
  версия не отвечает на `/healthz`, скрипт возвращает стенд на этот тег и
  завершается с ошибкой. Схему БД откат не трогает: миграции уже накачены,
  отмены у них нет (A-100). Обратно совместимая миграция это переживает,
  несовместимая требует разбора вручную - о чем скрипт и сообщает.

  Первое наполнение демо-данными (Прил. Б) после деплоя:

  ```bash
  SEED_PASSWORD=... podman compose -f docker-compose.prod.yml run --rm api seed
  ```

### Проба прод-контура без хоста

Прод-стенд поднимается целиком на машине разработчика - этим найдены три отказа,
которые чтение YAML не показывало (T75). Отличий от прода два, и оба в `.env`:
`TOU_DOMAIN=localhost` (Caddy выдает сертификат внутренним CA и не ходит
в Let's Encrypt) и `REGISTRY=localhost/tou-rent` с `TAG=local` - образы собираются
на месте, реестра нет.

```bash
cd infra/compose && cp .env.prod.example .env   # заполнить любыми значениями
podman compose -f docker-compose.prod.yml build api web
podman compose -f docker-compose.prod.yml up -d
```

Пароль Redis попадает в URL подключения - только буквы и цифры (см. `.env.prod.example`).
Дальше проверяется то же, что проверял бы смоук на хосте: `curl -k https://localhost/`
и `https://localhost/api/v1/healthz`, заголовки безопасности, `redis-cli` без пароля
(должен отбиваться), Object Lock на `dossiers` и права ключа приложения.

`deploy.sh` так не проверить: он начинается с `compose pull`, а тянуть локальные
образы неоткуда - пулл, откат и окно заморозки под живыми торгами остаются за T49.

Убирать за собой обязательно - вместе с томами, иначе объект, попавший в `dossiers`
под compliance-блокировкой, останется на диске на пять лет:

```bash
podman compose -f docker-compose.prod.yml down -v && rm -f .env
```
