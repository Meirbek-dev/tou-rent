## 2. Топология

```
пользователи ── HTTPS ──▶ Caddy (rent.tou.edu.kz, TLS, /api без буферизации - SSE и WS)
                            ├─▶ web  - TanStack Start SSR (публичный портал + кабинеты)
                            └─▶ api  - Rust/Axum (REST + SSE-уведомления + WS-аукцион)
                                  ├─▶ PostgreSQL   (все авторитетные данные, RLS, аудит, pgcrypto)
                                  ├─▶ Redis 8      (сессии, rate-limit, шина событий)
                                  └─▶ RustFS       (бакеты public / dossiers; Object Lock compliance 5 лет)
                            jobs - воркер: эскалация просроченных сроков (FR-1702),
                                   снятие публикаций через 6 мес. (INV-076, FR-1403),
                                   закрытие торгов с истекшим таймером (INV-066),
                                   сверка hash-цепочки аудита (INV-A01)
                            zitadel + zitadel-login - провайдер идентичности (профиль compose)
Zoom (внешний)  - ссылка на конференцию и на запись хранятся в карточке торгов (FR-306)
Sentry, PostHog (внешние SaaS) - ошибки и продуктовая аналитика фронта
GitLab (self-managed) - код, CI, Container Registry, деплой по SSH на хост
```

Один хост, `podman compose`, без Kubernetes: ≈500 внутренних пользователей, <1000 договоров/год, единичные одновременные аукционы. Тома PostgreSQL и RustFS - на дисках хоста.

**Экземпляров api может быть несколько** (NFR-12, T58): эфемерные события расходятся между процессами через Redis pub/sub, а до сокета доходят локальным broadcast (§ 5.4). Рестарт по-прежнему рвет открытые подписки - клиент восстанавливает состояние историей уведомлений и снапшотом комнаты (NFR-05). Достаточность одного экземпляра для заявленной нагрузки (NFR-02) остается неизмеренной (ТЗ v2 T59).

## 3. Архитектурные принципы

Принципы v1–v2 сохраняются и подтверждены реализацией:

- **compile-time прежде runtime** - статусы тендера как typestate, закрытые перечни как enum без catch-all, деньги отдельным типом;
- **БД - последний рубеж** - каждый инвариант Правил закреплен на самом нижнем достижимом уровне: тип → constraint/триггер → тест (23 инварианта, `specs/INVENTORY.md`);
- **один источник истины на факт** - контракт из utoipa, статусы из `refdata`, время из доменного `Clock`;
- **чистое ядро без IO** - `crates/domain` не знает про SQLx, Axum и Redis;
- **сроки - данные** - `core.obligations` вместо разбросанных проверок дат;
- **bleeding edge с якорями отката** - § 11.

Следствие отсутствия человеческого ревью: **пайплайн = ревью**. Любое свойство, которое проверил бы сеньор, выражено гейтом (§ 9). Файлы, определяющие сами гейты, выделены в защищенные пути - MR, трогающий их, требует аппрува инженера-контролера. Это единственная ручная контрольная точка.

**Честная оговорка.** Принцип «пайплайн = ревью» пока не действует: пайплайн ни разу не выполнялся на живом раннере (ТЗ v2 § 2.1). До подключения раннера единственным фактическим контролем остаются локальные прогоны и живые проверки в дев-стенде.

### 5.2 Расслоение: `ports` и `application`

Крейты `ports` (traits к IO) и `application` (сценарии) - не половина брошенного рефакторинга, а **осознанный пилот на одном сценарии**: `NotifyAdmitted` (FR-504) собран как use case, который знает только о портах `NotifyAdmittedStore` и `NotificationPublisher`. Он доказывает, что расслоение работает без Axum и SQLx в сигнатурах, и служит образцом.

Правило на будущее: **новые сценарии, у которых больше одного вызывающего или больше одного адаптера доставки, пишутся через `ports`/`application`; остальное остается в `http` + `db`.** Массовый перенос существующих обработчиков не планируется - он дал бы диффы без изменения поведения, что противоречит правилу «MR ≤ 400 строк, одна задача - один MR». Граница проверяется тем, что `crates/domain`, `crates/ports` и `crates/application` не имеют в зависимостях ни axum, ни sqlx.

### 5.3 Статусы и уведомления

Статусы тендера - typestate в `domain` (единый макрос порождает методы переходов и таблицу `TRANSITIONS`) + enum и триггер переходов в БД; тест сверяет таблицу из Rust с `refdata.tender_status_transitions` (INV-021, защита от рассинхрона).

Уведомления - enum `NotificationChannel { InApp }`; запись всегда в `core.notifications` (доказательная база, аудит-триггер), доставка in-app - SSE + счетчик непрочитанных. Расширение на Email/Telegram (FR-1303, задача T41) заставит компилятор дописать все ветки.

### 5.4 Реалтайм: локальная доставка, межпроцессная шина

SSE-уведомления и лента WS-комнаты доходят до подписчика через `tokio::broadcast` - это самый короткий путь до сокета, уже открытого этим процессом. Между экземплярами api события расходятся через Redis pub/sub (каналы `tou:notify` и `tou:auction`): публикация уходит в Redis и возвращается **всем** экземплярам, включая опубликовавший. Путь доставки поэтому один, дублей не возникает, а «свое» событие не требует особого случая.

Комната опознается полем сообщения, а не отдельным каналом: открытие новой комнаты не меняет подписку. Ценой этого каждый экземпляр видит события всех комнат - при единичных одновременных аукционах (ответы № 7, 8) это дешевле динамических подписок.

Обработчик про шину не знает: он по-прежнему зовет `notifier.publish` и `auction_hub.publish`. Без Redis (дев-стенд, тесты) те же вызовы доставляют события в пределах процесса.

Потеря эфемерного события не теряет факта: уведомление уже записано в `core.notifications`, ставка - в `core.bids`. Ошибка шины логируется и ничего не откатывает; клиент дотягивает пропущенное историей и снапшотом комнаты по `bid_id` (NFR-05).

### 5.5 Подпись документов

ЭЦП НУЦ РК вне периметра (ответ № 10). Юридически значимые документы - печатные формы Typst + скан подписанного экземпляра. Задел: `domain::signing` - `SignatureStatus` (`unsigned` / `paper` / `electronic`), трейт `SigningProvider` и заглушка `PaperSigning`, которая всегда отказывает. У договоров и актов есть `signature_status`, выводимый из наличия скана триггером `core.sync_signature_status` (то же правило продублировано типом, паритет под тестом). У протоколов поля нет: их скан система не хранит, а поле без источника - фикция. Подключение реальной подписи в контуре 5 добавляет реализацию порта и вариант enum, но не переделывает модель документа.

## 6. Данные

PostgreSQL, схемы `core` / `audit` / `refdata`; 39 миграций `sqlx migrate`, линт Squawk на новых миграциях. Все ID - uuid v7 (`uuidv7()`), деньги - `numeric(14,2)` KZT, времена - `timestamptz` (UTC в БД, Asia/Almaty в отображении).

### 6.1 Версия СУБД **[решение]**

Dev, CI и прод-compose используют `postgres:19beta2` (ADR-0002 писался под «19 в dev, 18 в прод», фактически прод-compose тоже на 19beta2). Это дает паритет окружений, но означает бета-версию СУБД в продуктивной эксплуатации. Решение инженера-контролера: либо дождаться 19 GA до первого прод-деплоя, либо перевести прод на 18 и принять расхождение мажорных версий. До решения деплой на прод не выполняется (он и так не выполнялся). Единственная зависимость от 19 - отсутствует: `uuidv7()` есть в 18.

### 6.2 Время: `core.now()`

Все правила сроков и все юридически значимые отметки берут время из
`core.now()` - это `now()` плюс сдвиг из `refdata.clock_offset`. На проде
строка сдвига нулевая, и `core.now()` вырождается в `now()`; сдвиг нужен
только сквозным сценариям, которым иначе не перешагнуть окно FR-303
в десять календарных дней (T68).

Возможность двигать время - это возможность подделать юридически значимую
отметку, поэтому она закрыта тремя рубежами (ADR-0005): роль приложения
не имеет права писать в таблицу сдвига; подкоманда `api time-shift`
требует `ALLOW_TIME_SHIFT=1`, которой на проде нет; сама таблица
аудируется наравне с мутациями домена.

Правило для нового кода такое же, как с `SystemTime::now` в Rust: в правилах
и отметках вызывается `core.now()`, а не `now()` - иначе половина сроков
живет в одних часах, а половина в других. Так и вышло на первом заходе:
миграция T68 перевела триггеры, а 57 умолчаний колонок и восемь функций
остались на часах процесса. Теперь правило держат два рубежа - тест
`clock_single_source` по схеме поднятой БД и grep-гейт G2 по новым
миграциям.

### 6.2 Инварианты на уровне СУБД

```sql
--   поверх - pgcrypto с ключом тендера (мастер-ключ в окружении, GUC)            INV-040
-- Ставки аукциона: append-only, CHECK amount > 0, триггер amount >= prev_max+step INV-063
-- Таймер торгов: стоп-время и «продление не более одного раза»                    INV-066
-- Один объект не сдается на пересекающиеся периоды (EXCLUDE USING gist)           INV-DB-02
-- Депозитная книга: двойная запись (debit XOR credit), баланс не меньше нуля      INV-DB-05
-- audit.log: append-only, row_hash = sha256(prev_hash || payload) + verify_chain() INV-A01
-- Голос члена комиссии ∈ {за, против}; договор не подписывается без сверки;
--   срок инвестдоговора ≤ 7 лет; особые условия участка неизменяемы  INV-055/115/094/105
```

Аудит-триггеры стоят на таблицах перечня INV-AUDIT (`specs/INVENTORY.md`), полноту перечня проверяет тест G15. Правки справочников тоже аудируются: МРП, календарь и версии коэффициентов определяют все будущие деньги и сроки. У `refdata.mrp` и `refdata.holidays` естественные ключи, поэтому для них - вариант `audit.record_natural_key()` (ключ внутри payload, `row_id` пуст); у версий коэффициентов есть `id`, там работает общий триггер.

**Справочники append-only для приложения.** Роль `tou_rent_app` не имеет права `DELETE` на `refdata`: версия множителя не удаляется, а добавляется - это тот же рубеж, что FR-202. Мутации справочников имеют варианты `*_on` для транзакции вызывающего, чтобы тест мог выполнить сценарий и откатить его.

Справочники `refdata`: МРП по годам, коэффициенты Прил. 4 (версионированные `effective_from`), производственный календарь РК (`add_business_days` - SQL и Rust с тестом паритета G12), таблица переходов статусов, закрытые перечни (основания отклонения, возврата, несостоявшегося тендера, категории особого порядка, изменяемые допсоглашением поля, особые условия участка). **Справочники - данные, а не код**: значения из Правил заводятся без правки Rust; редактирование МРП, коэффициентов и календаря - кабинет админа (FR-1901).

Redis - только эфемерное (сессии, шина событий, rate-limit): потеря инстанса не теряет данных. RustFS (ADR-0006) - `public` (опубликованные PDF, снятие через 6 мес. джобом) и `dossiers` (материалы тендеров и решений, Object Lock в режиме compliance на 5 лет - ADR-0004).

## 8. Наблюдаемость

**Бэкенд** - нет. Стек `grafana/otel-lgtm` и весь экспорт OTLP сняты 09.08.2026 решением инженера: вместе с ними ушли слой RED `http.server.request.duration` и бизнес-метрика `tou.tenders.count`. У api нет метрик и трейсов; наблюдаемость сводится к логам `tracing` в stdout контейнера. NFR-02 подтверждается разовым нагрузочным прогоном T59.

Ограничение, которое отсюда следует: NFR по времени отклика проверяются только нагрузочным прогоном вручную, непрерывного измерения задержек и доли ошибок в проде нет.

**Фронтенд** - Sentry (`@sentry/tanstackstart-react`, серверная инструментация через `instrument.server.mjs`) и PostHog. Это добавление относительно v2, и оно требует дисциплины по NFR-07: во внешние SaaS не должны уходить персональные данные из форм заявок. Правило: события PostHog содержат только идентификаторы и имена действий; Sentry-события проходят через `beforeSend`, вычищающий тела запросов и значения полей. Ключи проектов - переменные окружения; при их отсутствии оба интегратора выключены (дев-контур и CI работают без внешних сервисов).

## 10. Деплой

`infra/compose/deploy.sh`: пулл образов из GitLab Registry → миграции отдельным сервисом `api-migrate` (тот же образ, команда `migrate`) → `podman compose up -d` → ожидание `/healthz` у **обоих** контейнеров трафика, api и web. Выполняется из GitLab CI по SSH. **Окно заморозки:** деплой блокируется, пока жива хоть одна комната торгов (`core.auctions.status = 'running'` и срок не истек) - заморозку задает комната, а не статус тендера, который может висеть в `trading` с уже завершенными торгами (обход - `DEPLOY_FORCE=1`). **Откат:** тег, прошедший проверку здоровья, пишется в `.deployed-tag`; при отказе стенд возвращается на него, схему БД откат не трогает (A-100).

Образы: `infra/docker/api.Dockerfile` (Rust, сборка в `rust:1.98.0` → запуск на debian-slim; в нем же едут миграции и воркер `jobs`) и `web.Dockerfile` (сборка и запуск на Bun - сервер nitro/srvx собирается под тот рантайм, в котором шла сборка). Секреты прод-стенда - `.env` рядом с compose-файлом, в репозиторий не попадает; шаблон - `.env.prod.example`.

Контейнеры ограничены (T74): потолки памяти под хост с 16 ГБ (A-099), `no-new-privileges` и `cap_drop: [ALL]` с точечными исключениями - Caddy оставлен `NET_BIND_SERVICE`, Postgres минимум для штатного входа образа, Redis запускается сразу от `redis` (A-101). Сам контур поднимался целиком локально 10.08.2026 (T75): это нашло три отказа, которых чтение YAML не показывало, - несобиравшийся образ `web`, падавший на старте Redis и вечно unhealthy `jobs`.

Долги контура 4: job публикации образов в Registry (A-029, T48), первый реальный деплой на хост (T49 - вместе с ним `compose pull`, откат и ACME на настоящем домене), pgBackRest + учебное восстановление (NFR-06, NFR-13, T51), SOPS+age для секретов и гейт gitleaks (NFR-09, T47). Пины тегов инфраструктурных образов из этого списка ушли - сделаны в T70.
